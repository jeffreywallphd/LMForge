\begin{abstract}
This report documents the decoder-model track of a document-processing pipeline whose \textbf{primary deliverable} is a synthetic question--answer (Q\&A) dataset suitable for training and fine-tuning custom language models. Long documents are segmented into overlapping chunks; four open, instruction-tuned \emph{causal} decoders (Phi-4-mini-instruct, Mistral-7B-Instruct-v0.3, Qwen2.5-7B-Instruct, Gemma~7B) are prompted to emit structured Q\&A conditioned on each chunk. The current protocol targets \textbf{one} Q\&A pair per chunk (earlier pilot runs used two pairs) and processes \textbf{900} chunk attempts per configuration for chunk sizes $\{128,256,512\}$ (chunk size 1024 uses 808 attempts in the exported success-rate log, reflecting the available chunk inventory for that setting).

We first evaluate the engineering outcomes that matter for dataset construction: \textbf{elapsed time}, \textbf{JSON parse success rate}, and automatic \textbf{quality} scores (including BERTScore F1 and ROUGE-L in the lab summary plots). These operational results determine which model configurations produce usable training rows at acceptable cost. A final section revisits multivariate statistics: because the quality metrics are highly correlated and classical MANOVA assumptions are often violated, we emphasize assumption-lean \textbf{PERMANOVA} and report an updated \textbf{cross-model} comparison (models contrasted at fixed chunk size) alongside supporting MANOVA/ANOVA summaries.
\end{abstract}

\section{Introduction}

The practical goal of this project is to build a \textbf{synthetic supervised dataset}: for each text chunk drawn from domain PDFs, we want a model-generated question and a model-generated answer that can be filtered, deduplicated, and merged into downstream training corpora for customized assistants. Decoder-only instruction models are a natural choice because they can follow a fixed prompt template, control output length via \texttt{max\_new\_tokens}, and emit structured payloads (JSON) that downstream tooling can parse into rows.

This report is organized to mirror that priority. Sections~\ref{sec:protocol}--\ref{sec:lab-results} focus on dataset-generation \textbf{throughput and reliability} (did we get valid examples?) and \textbf{quality proxies} (are those examples aligned with the chunk under automatic metrics?). Only afterward do we summarize multivariate inference (MANOVA/PERMANOVA), which is useful for understanding how models differ jointly across correlated metrics, but is not the operational bottleneck when a run fails JSON validation.

\section{Task definition}
\label{sec:task}

The decoder receives a single text chunk (and a fixed prompting template) and generates \textbf{one} question--answer pair under the current protocol (earlier experiments requested two pairs per chunk). Outputs are expected in a parseable structured format (JSON), so a ``successful'' row is not only semantically reasonable but also \textbf{machine-valid}. Reference answers implied by the chunk text are used together with model outputs in standard automatic metrics. The task emulates retrieval-augmented generation in which the retriever supplies one chunk per query, so conclusions apply to ``single-chunk context'' settings rather than full-document prompts.

\subsection{Source material and chunking}

Experiments use chunked passages derived from PDF text prepared in the lab's segmentation workflow (\texttt{Generate\_Paragraphs/} notebook and JSON under \texttt{Generate\_Paragraphs/Results/}). Chunk stores are keyed by source PDF path; nominal chunking levels $128$, $256$, $512$, and $1024$ select among files such as \texttt{extracted\_chunks\_<size>\_overlap.json}. Each experimental cell corresponds to a combination of chunk level and a chosen maximum number of new tokens allocated to decoding.

Chunking is implemented by extracting plain text from PDFs, concatenating pages, then applying a recursive text splitter with a \textbf{target size expressed in words} but approximated using a fixed average characters-per-word constant. Overlap is set as a fixed fraction of the chunk size (15\%). Splitting prefers boundaries in the order: paragraph breaks, line breaks, sentence boundaries, spaces, then (as a last resort) character-level splits. A light filter removes obviously non-content chunks (e.g., short fragments, numeric/punctuation-only strings, and copyright boilerplate or trailing references headings).

\subsection{Stored outputs}

For each configuration, generations are logged as JSON files (e.g.\ \texttt{generation\_log\_<chunk>\_Token\_<maxtok>\_Q1.json}) mapping source paths to chunk text and \texttt{qa\_pairs}. Run manifests such as \texttt{qa\_run\_tracker\_detailed.csv} record success and failure counts per cell, supporting auditability across lab machines and run IDs (\texttt{NEW\_RUNS\_LMForge\_RUN01\_Lab\_Machine}, \texttt{RUN02}, \texttt{RUN04}, etc.).

\section{Experimental protocol (dataset generation)}
\label{sec:protocol}

\subsection{Models and factor grid}

We evaluate four Hugging Face causal instruction-tuned checkpoints (Table~\ref{tab:decoder-pool}). Each model is run across a grid that crosses chunk sizes $\{128,256,512,1024\}$ with multiple \texttt{max\_new\_tokens} budgets (e.g.\ $128,256,512,1024,2048$), yielding one experimental cell per (model, chunk size, token budget) combination.

\subsection{Sample size per cell}

The lab's exported success-rate accounting (\texttt{other/Lab\_Report\_2/Results/Results.txt}) uses \textbf{900} chunk attempts for most cells at chunk sizes 128--512. At chunk size 1024, the log shows \textbf{808} total chunks for several models, reflecting the number of available 1024-width chunks under the current PDF inventory and filtering rules (not a modeling hyperparameter).

\subsection{Protocol evolution (what changed since earlier write-ups)}

Earlier pilot runs processed on the order of \textbf{1800} chunks per iteration and requested \textbf{two} Q\&A pairs per chunk. The current protocol reduces the per-cell attempt count to \textbf{900} and requests \textbf{one} pair per chunk. This generally reduces generation cost per cell, simplifies JSON validation, and changes the interpretation of ``failures'' (fewer required fields per success).

\subsection{Summary of what ``good'' means for dataset construction}

For downstream dataset assembly, the dominant constraints are usually:
\begin{itemize}[noitemsep]
    \item \textbf{Reliability:} high fraction of parseable JSON outputs (low failure rate).
    \item \textbf{Throughput:} wall-clock time per cell (and therefore cost per accepted row).
    \item \textbf{Quality proxies:} automatic scores such as BERTScore F1 and ROUGE-L on accepted rows.
\end{itemize}

\section{Evaluation metrics for multivariate analysis}

Each aggregated analysis cell contributes a vector of eight dependent variables (cell means over accepted/scored items):
\begin{itemize}[noitemsep]
    \item ROUGE-1, ROUGE-2, ROUGE-L, ROUGE-Lsum;
    \item BERTScore precision, recall, and F1;
    \item STS score (embedding-based similarity).
\end{itemize}

ROUGE and BERTScore capture n-gram and token-level overlap with references; STS summarizes semantic proximity. Together they support a multivariate profile of quality, at the cost of substantial correlation among components (especially among ROUGE variants).

\section{Discussion (dataset generation first)}

Three practical points follow from Section~\ref{sec:lab-results} for teams building training corpora.

First, \textbf{optimize for usable rows, not only metric scores}. Qwen illustrates how strong semantic scores on accepted outputs can coexist with low JSON success rates; unattended dataset generation may require aggressive repair/retry logic.

Second, \textbf{token budget and chunk width interact with reliability}. The success-rate surface is not monotone in every model; Mistral's reliability at moderate/high token budgets is a primary reason it is attractive as a default generator.

Third, \textbf{protocol changes matter}: reducing pairs-per-chunk from two to one and reducing per-cell attempts from $\sim$1800 to 900 changes cost and failure modes; always quote success rates from the same protocol version as the plotted metrics.

\section{Conclusion (dataset generation)}

The decoder stage exists to produce structured Q\&A training examples under a repeatable prompt and schema. The lab's up-to-date reliability and timing plots (Section~\ref{sec:lab-results}) are the first artifacts to consult when choosing a default generator and decoding budget. Multivariate analyses below provide additional context on how models differ jointly across correlated quality metrics.

\section{Statistical validation}

\noindent The subsections below summarize the \textbf{per-model} multivariate diagnostics and PERMANOVA framing used in the analysis notebooks (primarily for comparing chunk-size regimes within a fixed model on aggregated metric vectors). This is complementary to the cross-model tests in Section~\ref{sec:cross-model-multivariate}, which hold chunk size fixed and compare models.

\subsection{Exploratory and association structure}

Line plots and boxplots relate chunk size and max-new-token settings to BERTScore F1. Correlation heatmaps and VIF quantify redundancy. Reported VIFs for ROUGE components are very large, flagging linear multicollinearity that complicates interpretation of individual MANOVA coefficients.

\subsection{MANOVA assumptions}

\textbf{Multivariate normality} is assessed with the Henze--Zirkler test. In the archived summaries, normality is rejected for Gemma, Mistral, and Phi (very small $p$-values), while Qwen2.5 does not reject at $\alpha=0.05$ ($p\approx 0.09$).

\textbf{Homogeneity of covariance} is assessed with Box's~M; the saved output rejects equal covariances across chunk-size groups for all models, with $\chi^2$ reported as infinite in the log (numerical overflow under severe heterogeneity).

\textbf{Outliers} are flagged via Mahalanobis distance; approximately $25\%$ of the $N=20$ observations exceed the threshold at $p<0.001$ in each model's \texttt{outlier\_summary.csv}.

\subsection{MANOVA (Type III)}

Type~III MANOVA tables (Wilks' $\Lambda$, Pillai, Hotelling--Lawley, Roy) are computed for completeness. Because covariance homogeneity and outlier rates are problematic, these results are \emph{not} treated as the primary confirmatory basis.

\subsection{PERMANOVA}

PERMANOVA tests whether chunk-size groups differ on the \emph{joint} metric vector using permutations of Euclidean distances among z-scored outcomes. The omnibus pseudo-$F$ and permutation $p$-value are the main inferential summaries. Pairwise PERMANOVA contrasts adjacent and extreme chunk sizes; $p$-values are permutation-based and, with $B=999$, floor at $0.001$ when no permuted statistic exceeds the observed value.

\subsection{PCA}

PCA projects the dependent variables into two dimensions for visualization and supports auxiliary MANOVA on the first components where recorded in \texttt{statistical\_summary.txt}.

\section{Discussion (multivariate follow-up)}

Four substantive points complement the dataset-generation discussion.

First, \textbf{decoder choice matters even at fixed chunk size}. Cross-model PERMANOVA rejects equality of multivariate performance profiles at every chunk size (Table~\ref{tab:cross-permanova-omnibus}), and the pairwise table shows that some separations are robust across multiple chunk sizes (notably contrasts involving Qwen2.5 versus other models).

Second, \textbf{chunk size remains a first-order lever} in the descriptive metric profiles: mean tables show large drops between 128- and 1024-size chunks across models, consistent with the hypothesis that smaller local contexts yield more extractive, metric-friendly QA behavior under this protocol.

Third, \textbf{classical MANOVA should be treated as secondary}. Metric collinearity, heteroskedasticity across groups, and outlier prevalence can make parametric multivariate inference fragile. Distance-based PERMANOVA on standardized outcomes aligns better with the data geometry while still testing a meaningful multivariate null.

Fourth, \textbf{pipeline integration}: chunk size and model selection should be co-designed with the encoder filtering stage. Smaller chunks may score better partly because they localize answerable content; the encoder filter and the decoder configuration jointly determine whether QA generation behaves as extraction, paraphrase, or hallucination under automatic metrics.

\section{Conclusion (multivariate analysis)}

Aggregated quality metrics are strongly correlated; multivariate tests are most useful as a structured sanity check on ``overall separation'' between models and chunking regimes. Future work should enlarge $N$, add prompt variants, and validate automatic metrics against human judgments.
